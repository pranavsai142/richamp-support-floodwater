# What we use / need — triage search model

This is the **meta lens** for Unity estate triage. Not a complete catalog of every script — a map of *families* of significant work so we know what to keep, what is bulk, and what is junk.

Sister context: coastal full fidelity = **ADCIRC (+SWAN)** runs + **this postprocess repo**. Atmosphere = CloudVision.

**Scientific crest (thesis):** why Napatree runup and three-water differencing matter — [thesis-wave-runup-crescendo.md](thesis-wave-runup-crescendo.md).

---

## North-star desert-island outcomes

If the multi-TB estate vanished tomorrow, we still want to:

| Outcome | Meaning |
|---------|---------|
| **Stand up Floodwater again** (primary) | Configs + mesh packs + binaries + this postprocess attach |
| **Stand up ASGS again** (secondary; may never) | ASGS tree / machine profile + richamp POSTPROCESS hooks (`README.md`) |
| **Run binaries** | Working `padcirc` / `adcirc` / `adcprep` (+ SWAN-coupled builds if used) |
| **Rebuild ADCIRC(+SWAN)** | Source tree that was actually used + build recipe (not five clones) |
| **Re-execute significant cases** | Inputs + scripts for thesis/golden runs — **not** whole finished PE* / fort.63 dumps |
| **Postprocess any rundir** | Point tools at a folder; products + obs |
| **Wind / rain / track side kit** | Library of fields + converters into ADCIRC-usable formats |

**Preserve significant work.** Experiment trees (self-builds, ScratchCopy thesis cases, custom configs) count as significant. Duplicate test-build clones and failed suite trash do not.

## Two primary postprocess entry points

### A — Manual / “point at a rundir” → `localGenerator.sh`

**Role:** Human-driven postprocessing when you already have a **manual run folder** (or any ADCIRC/SWAN product directory).

- Lives in **this repo** at root: `localGenerator.sh`
- Operationally a **recipe book**: uncomment/edit lines that call `generateGraphs.py`, `scale_and_subset.py`, runup, waves, wind, water, obs, etc.
- Inputs are **paths into a rundir** (or staged products), e.g.:
  - Water: `fort.63.nc`
  - Mesh: `fort.14`
  - Waves: `swan_HS.63.nc`, `swan_DIR.63.nc`, `swan_TMM10.63.nc`, `swan_TPS.63.nc`, `rads.64.nc`
  - Wind: GFS / RICHAMP / fort.74-class products
  - Stations: `OBS_STATIONS.json`, `NAPATREE_*`, runup station sets
- Core driver: **`generateGraphs.py`** (+ Readers, Graphers, GetObs*, GetRunup, …)

**Triage implication:** For a significant case, keep a **re-run kit** (inputs + sbatch scripts + fort.14/15/22 + swaninit + hotstart recipe), not the multi-TB PE* tree. Postprocess only needs the **products** (`fort.63.nc`, swan `*.63.nc`, etc.) when graphing — and those can be regenerated by re-running.

**Thesis / ScratchCopy example:**  
`AdcircManualRuns/Aug29ScratchCopy/pranav_sai_uri_edu-runup/` (~156 GiB *filtered*, still huge) holds Dec2022 / Dec2023 / Erin / temps.  
User intent: **part with bulk**; keep what is needed to **execute again** (even if wall-clock is long). Do **not** full-download ScratchCopy.

### B — Floodwater / ASGS full pipeline → `richamp_scale_and_subset*`

**Role:** The **real Floodwater end-to-end postprocessing** path (orchestrated / scenario dir).

| Piece | Role |
|-------|------|
| `richamp_scale_and_subset.sh` → `.scr` | After forecast: subset fort.63, max inundation (Matlab), copy products to `RICHAMP_OUTDIR` |
| `richamp_scale_and_subset_post_init.sh` → `.scr` | Alongside forecast: `generateRunProperties`, MetGet / GFS or NHC parametric wind via `windgfdl`, `scale_and_subset.py`, rain, track shapefiles |
| `run.sh` / `scenarioFileGenerator.sh` | Scenario wiring (`RICHAMP_INDIR`, `RICHAMP_OUTDIR`, `SCENARIO_WIND`) |
| Static assets | `NLCD_z0_RICHAMP_Reg_Grid.nc`, `gfs-roughness.nc`, `diag_parm.nml`, `windgfdl` (see root `README.md`) |

ASGS install path documented in root **`README.md`** (POSTPROCESS / INITPOST hooks). Floodwater configs live largely under **home** (`floodwater_files`, `ecflow_configs`) and project mirror `floodwater_files`.

**Triage implication:** Home Floodwater/ecflow/ASGS config trees are **P0** for pathway B — small and irreplaceable relative to PE* bulk.

## Side-tool families (look for these everywhere)

Supplemental tools — not always on the critical path of a live Floodwater cycle, but they **are** significant research infrastructure. When scanning Unity or the Unity copy of this repo, classify artifacts by **family**:

**Pull still running** (tmux `unity-pull`, home rsync). Remaining rsync is largely completing/syncing noise + bulk (miniconda, etc.), not “waiting for Floodwater to appear.”

| Home/work content | Need for desert island? |
|-------------------|-------------------------|
| `floodwater_files`, `ecflow_configs`, `asgs_files`, `scripts/*flood*`, `asgs-global.conf` | **Yes — P0** (small) |
| `projects/asgs`, machine profiles (`custom-intel-unity*`) | **Yes — P0/P1** for rebuild/ASGS |
| Unity `projects/richamp-support*` unique extras | **Selective P1** (diff vs git) |
| `miniconda3` | **No** — reinstall; often dominates time/bytes |
| Desktop/Downloads/Music/Videos/ondemand | **No** |
| `ecflow_output` under home | Mostly **P2/P3** (project has bulk too) |
| work `scenario_files` winds / scenarios | **P1 library seed** |
| work `ECFLOW` bulk / huge out trees | **P2** at best |

### Recommendation

- **Do not need a perfect full home+work mirror** for the north star.
- **If rsync is still chewing miniconda / Desktop noise:** cancel is reasonable; follow with a **surgical gem rsync** (configs, projects/asgs, floodwater, scripts, scenario wind packs, binaries).
- **If home gems already landed and only tail remains:** finishing home is fine; still **skip treating miniconda as sacred**.
- **Never** auto-start full ManualRuns after home/work.

Working cases live on the external-drive archive (bootstrap / t1 tiers under `unity-archive/`). Full remote mirrors are optional insurance, not the product.

## How to use this doc when triaging a folder

Ask, in order:

1. **Is this on pathway A (manual + localGenerator) or B (Floodwater + richamp_scale_and_subset)?**  
2. **Is it a side-tool family artifact** (wind, rain, track, run props, runup, obs, Matlab)?  
3. **Is it unique significant work** (thesis case inputs, self-build, wind that took effort)?  
4. **Can postprocess or a re-run regenerate it** (PE*, fort.63 fields, temp graphs)?  
5. **Is there a newer sibling or a third clone?**

Then assign P0–P3 using [project-triage-rubric.md](project-triage-rubric.md). Top-level table: [unity-project-triage-inventory.md](unity-project-triage-inventory.md).
